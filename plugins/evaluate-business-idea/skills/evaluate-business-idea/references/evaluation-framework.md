# 五維深度系統評估框架

完整版定義。SKILL.md 是入口，這份是評估時的查照手冊。

## 核心問題

> **拔掉這個系統，客戶會怎樣？**
>
> - 「換一個就好」→ 免洗系統
> - 「業務會中斷」→ 深度系統

## 五個評估維度

### 維度 1：人力替代性

**核心問題**：拔掉這個系統，客戶要補回幾個人？

| 分數 | 判定 |
|------|------|
| 0 | 0 人，只是方便、加速、提升體驗 |
| 1 | 省半個人（節省顯著工時但無法淘汰一個職位） |
| 2 | 直接淘汰 ≥ 1 個全職人力 |

**判分要訣**：
- 不是「快了多少倍」而是「省了幾個人頭」
- 想像客戶 HR 報告：「因為導入這套系統，我們少請了幾個 X 職位的人？」
- 「方便很多」→ 0 分，因為人沒少

### 維度 2：數據累積性

**核心問題**：用越久，這個系統會變得越有價值嗎？

| 分數 | 判定 |
|------|------|
| 0 | 否，每次都是一次性使用，沒有累積 |
| 1 | 部分累積（歷史紀錄、log、查詢用） |
| 2 | 強累積（模型越用越準、知識庫長大、規則庫成熟） |

**判分要訣**：
- 一次性工具（發票 OCR、PDF 切割）→ 0 分
- 純歷史紀錄（操作 log，看了沒下一步）→ 1 分
- 學習型（推薦準度 +、模型 retrain、user behavior 累積）→ 2 分

### 維度 3：流程嵌入度

**核心問題**：客戶組織的 SOP 是不是「長」在這個系統上？

| 分數 | 判定 |
|------|------|
| 0 | 否，拔掉就換一個，業務不受影響 |
| 1 | 部分流程依賴，拔掉會卡但能繞 |
| 2 | 完全依賴，拔掉要重新訓練整個團隊 |

**判分要訣**：
- 「業務開晨會看的儀表板」→ 1-2 分
- 「整個請款流程都跑在系統上」→ 2 分
- 「員工每天用，但拔掉用 Excel 也能做」→ 0-1 分
- 看新人 onboarding 教什麼：教這個系統 = 流程嵌入

### 維度 4：決策編碼

**核心問題**：「人腦裡的規則」有多少被編碼進系統？

| 分數 | 判定 |
|------|------|
| 0 | 否，所有判斷都還在資深員工腦裡 |
| 1 | 部分規則已編碼（簡單 if/else、表單流程） |
| 2 | 核心判斷邏輯已在系統中（業務知識、領域 know-how） |

**判分要訣**：
- 純資料展示 → 0 分
- 表單驗證、簡單分類 → 1 分
- 「這個案件要怎麼處理」這種需要老師傅才知道的判斷 → 2 分
- **這維度最值錢**，因為它把「人才依賴」變成「系統資產」

### 維度 5：重建成本

**核心問題**：要做一套同樣水準的系統需要多久？

| 分數 | 判定 |
|------|------|
| 0 | < 1 個月，週末就能做出來 |
| 1 | 1-6 個月（需要團隊 + 整合） |
| 2 | > 6 個月，甚至實質不可能（資料 / know-how / 在地化壁壘） |

**判分要訣**：
- 「能不能做」 vs 「能不能做到一樣好」是兩件事
- 資料壁壘（多年累積）+ know-how 壁壘（業務理解）= 重建很難
- 純技術型方案重建容易，整合型 + 流程型很難

## 判定標準

```
8-10 分 → 🟢 深度系統 → 全力投入
5-7 分  → 🟡 有潛力   → 做，但必須規劃「如何加深」路徑
0-4 分  → 🔴 免洗系統 → 不做，或只做買斷賺時間差
```

## 紅線檢驗（不可違反）

不論總分多少，以下兩條紅線必過，否則不能歸為深度系統：

1. **維度 1（人力替代性）≥ 1**
   - 不能淘汰人 → 直接淘汰產品
   - 「方便」「快速」「精美」不是商業價值

2. **維度 2-5 總和 ≥ 4**
   - 否則就算總分 5+ 也只是「省人力的工具」，不是深度產品

> **底層信念**：真懂客戶才能做深度產品 — 訪談 > coding。

## 商業模式原則

### 核心思維：副產品，不是主業

```
自己用得好 → 有人問 → 順便賣
```

**避免的陷阱**：
- ❌ 為了外部客戶需求而開發新功能
- ❌ 投入大量資源做產品行銷
- ❌ 把工具販售當營收主力

> 如果你的本業很賺、工具是為了讓本業更賺，那工具就是副產品。
> 如果你想用工具當主業，那就是 SaaS 創業，遊戲規則完全不同。

### 定價哲學：價值定價（不是成本定價）

報價公式：

> 「如果你每週省下 ___ 小時，
>  你能把這些時間拿去做 ___，
>  這預計能為公司帶來 ___ 的價值。」
>
> **報價 = 客戶價值的 10-30%**

不要按「我寫 code 寫多久」報價，按「客戶省下多少」報價。

### 理想營收結構

| 類型 | 佔比 | 說明 |
|------|------|------|
| 一次性收入 | 40% | 諮詢 + 客製導入 |
| 持續性收入 | 50% | 訂閱月費（穩定現金流關鍵） |
| 加值收入 | 10% | 維護合約、進階功能 |

純一次性收入 = 不穩定；純訂閱 = 啟動慢。混合最健康。

## 紅旗（看到這些訊號就停下來）

評分時若發生以下情況，**停止打分**並回頭做更多功課：

- 「這維度沒辦法評，因為還沒做」→ 要補做調查或直接 0 分
- 同時想給多個維度高分但說不出具體理由
- 用「未來」「規劃中」幫現在加分（深化路徑可以講未來，打分要看現狀）
- 維度 1 = 0 但堅持要做 → 紅線檢驗失敗，這不是深度產品，要不要做的決策邏輯不一樣
- 把「我們很厲害 / 技術很難」當成高分理由 → 厲害但客戶不痛 = 沒生意
